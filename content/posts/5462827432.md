# 从"跑通"到"上线"的最后一公里，我经历了什么？
> 双ECS跨地域组网、子路径白屏、"看起来没坏"的回归
## 为什么选择"双节点"?

-   **备案规则**：国内服务器对外提供 Web 服务要先完成 ICP 备案，
未备案的域名解析到大陆服务器会被接入商拦截 80/443；
-   **租期短**：不满足`bei an`条件；
-   **组网**：云厂商的专线方案需要燃烧经费。

所以，我的选择是：先把`yu ming jie xi`指向香港入口节点，大陆业务节点通过私有隧道接入，不引入任何公网端口转发；再用自**建加密隧道**达到和专线等价的隔离效果。

## 架构全景

```
用户
  │  HTTPS
  ▼
香港 ECS（公网入口，唯一暴露面）
  ├── TLS 网关 / Nginx（80/443 放行全网，终结 TLS）
  └── WireGuard 隧道 10.10.0.0/24
        │（加密私有网络，无公网端口转发）
        ▼
国内 ECS（业务节点，零公网暴露）
  ├── 前端 Nginx（Vue 静态 + history 路由 + /api 与两条 WS 反代）
  ├── Go API / Chat / Notify 三服务（Docker）
  └── MongoDB（仅 Docker 内网可达）
```

## 安全组配置：
- **国内节点的业务端口 `5000/8001/8088/27017` 一律不对公网开放**
- 服务间走 Docker 内网，跨节点走 WireGuard 隧道；
- 22 端口默认关闭，调试时才放行"当前出口 IP 的 `/32`"，用完即回收。

## 坑 1：跨地域链路，每一环都"看起来能通"

### 现象

香港网关要经 WireGuard 访问国内ECS上的 Docker 服务，但表现为"能连通、请求却异常"。

### 根因：五层网络栈叠在一起

WireGuard 的 `AllowedIPs` / 路由、宿主机 `ip_forward`、Docker bridge 网络的可达性，**任意一环断了，表现都差不多**。

### 修复：逐段验证法

从外到内逐级 curl 定位断点：

```
网关侧（香港） → 隧道节点（WireGuard 对端） → 国内容器内网
```

实时链路还得再补一层：**双层 Nginx 下 WebSocket 要透传 `Upgrade` / `Connection` 头，并完成 HTTP/1.1 升级握手**——在 HTTP/2 场景下手动握手会返回 426。把这两件事做对，HTTP 与 WebSocket 跨节点才算真正打通。

> 经验：**跨网络栈的"能连通但异常"，高效的排查方式是从一端到另一端逐段打点**，而不是在某一层反复试。

* * *

## 坑 2：子路径部署导致的全站白屏——"HTML 冒充 JS"

### 现象

前端按 `/app/` 基路径构建（`publicPath` 与 vue-router 的 `history` base 对齐），准备平滑接入一个已在运行的 Nginx 网关。结果上线后**全站白屏**，控制台报错晦涩难懂。

### 根因：MIME 不匹配

前端构建后，`index.html` 引用的是 `/app/js/*`。而原有 nginx 的 `try_files` 会把"不存在的资源"**统一兜底回 index.html**——于是浏览器拿到的 JS/CSS 实际是 `text/html`，因为 MIME 不匹配被拒绝执行，页面就白屏了。

> **咱以为请求的是 JS，结果拿回来的是 HTML。**

### 修复：逐层核对 + 精确接管

-   核对"容器内文件布局 vs 响应 `Content-Type`"，定位到是 nginx 兜底逻辑在作祟；
-   把静态产物放进镜像内的 `/app` 子目录，用 `location /app/` **精确接管静态资源与 history 回退**；
-   用 `301` 完成 `/ → /app/` 的上线入口适配。

> 这套"路径前缀"而非"独占端口/域名"的接入方式，验证了多应用共网关上线的**低成本迁移路径**——存量业务完全不受影响。

## 坑 3：一个"点击毫无反应"的静默 bug

### 现象

线上出现"关注/取关按钮点击没有任何反应，也没有任何报错"。
> 这种**静默失效**单靠人工回归极难发现

### 根因

生命周期钩子被误放进了 `methods`，导致防抖函数**从未被初始化**。
> 逻辑没报错，但是代码没跑

### 修复：用 E2E 把行为钉死

我写了 Cypress 端到端用例做兜底，断言三层：

1.  点击后必须**真实发出 PATCH 请求**；
1.  按钮文案必须翻转；
1.  服务端 `followers` 数据必须真实变化。

### 结果："看起来没坏" → "可自动验证没坏"
> **防静默回归，靠的是对"行为结果"而非"有没有报错"做断言**

## 发布链路：从"手工提心吊胆"到"可校验、可回滚"

上线不是结束，因为**发布的过程**也可以被工程化：

-   **CI/CD**：GitHub Actions 串起「后端测试 → 前端 Cypress 端到端回归 → Docker 镜像构建推送」；
-   **镜像语义化标签** + **发布前镜像内容自检**：校验静态产物目录布局和 nginx 配置片段，拦截"构建缓存导致坏镜像上线"这类真实发生过的故障；
-   服务器侧拉取 → 上线，形成"代码提交 → 测试 → 镜像推送 → 服务器拉取"的自动化闭环。

## 最后：防火墙的"最优配置"长这样

> **"能不开就不开、开也限来源"** 

| 节点          | 端口                 | 策略                                                   |
| ------------- | -------------------- | ------------------------------------------------------ |
| 国内（业务）  | 22                   | 默认关，调试时仅放行当前出口 IP 的 `/32`，**用完即关** |
| 国内（业务）  | 5000/8001/8088/27017 | **一律不放行**（服务走 Docker 内网，跨节点走 WG 隧道） |
| 国内（业务）  | 80                   | 按需放行（正常流量走香港网关，平时可关）               |
| 香港（入口）  | 80/443               | 放行全网，TLS 终结在此                                 |
| WireGuard UDP | ——                   | 仅放行对端公网 IP                                      |

## 5条可复用经验

1.  预算和备案会反向塑造架构
2.  跨网络栈排障靠**逐段打点**，而非单层反复试；
3.  "200但内容不对"的故障(白屏)，先核对响应 `Content-Type`；
4.  防静默回归，要断言**行为结果**，而非"出现报错"；
5.  发布前对镜像做内容自检，把"坏镜像上线"从**事故变成**可拦截的**检查项**。
